# 802.1Q Q-in-Q Tunneling

[한국어](../09-802.1Q-Q-in-Q-Tunneling.md) | **English** | [日本語](09-802.1Q-Q-in-Q-Tunneling.ja.md) | [简体中文](09-802.1Q-Q-in-Q-Tunneling.zh-CN.md) | [Español](09-802.1Q-Q-in-Q-Tunneling.es.md) | [Français](09-802.1Q-Q-in-Q-Tunneling.fr.md)

**802.1Q tunneling (Q-in-Q)** is often used by Metro Ethernet providers to offer customers a **Layer 2 VPN**. The idea is simple: the provider adds **one more 802.1Q tag to every frame** it receives from a customer. By using a different VLAN tag per customer, the provider keeps customer traffic separated and carries it transparently across its network.

| Advantage | Description |
| --- | --- |
| Easy to implement | Works on ordinary switches, no special hardware |
| No routing needed | Unlike MPLS VPN, no routing protocol between provider and customer |
| Customer view | The two sites look **directly connected at Layer 2** |

> For the 802.1Q tag structure, read [03. 802.1Q Encapsulation](../03-802.1Q-Encapsulation.md) first.

---

## Lab topology

![Q-in-Q lab topology](../images/qinq/topology.png)

- **R1, R2**: customer sites (the customer uses **VLAN 12** between the sites)
- **SW1, SW2, SW3**: service provider network (all of this customer's traffic is carried in **VLAN 123**)

## How it works

![Q-in-Q tag flow](../images/qinq-tag-flow.svg)

1. R1 sends frames tagged with **VLAN 12**.
2. Provider switch SW1 adds another **VLAN 123** tag on top.
3. After passing SW3, SW2 **removes the outer tag (123)** and forwards R1's original VLAN 12 frame to R2.

Seen as frames:

![Q-in-Q frame](../images/qinq-frame.svg)

| Where | Frame |
| --- | --- |
| Customer → SW1 | Tag 12 (Inner, Customer) |
| SW1 ↔ SW3 ↔ SW2 trunks | **Tag 123 (Outer, Provider)** + Tag 12 |
| SW2 → Customer | Tag 12 |

## 1. Customer router configuration

R1 and R2 use **sub-interfaces** on subnet `192.168.12.0/24` and tag all frames as **VLAN 12**.

![R1 interface](../images/qinq/r1-interface.png)

![R1 sub-interface](../images/qinq/r1-subinterface.png)

![R2 interface](../images/qinq/r2-interface.png)

![R2 sub-interface](../images/qinq/r2-subinterface.png)

```
R1(config)#int g0/0
R1(config-if)#no shut
R1(config-if)#int g0/0.12
R1(config-subif)#encapsulation dot1q 12
R1(config-subif)#ip add 192.168.12.1 255.255.255.0
```

R2 is the same, only the IP is `192.168.12.2`.

## 2. Trunks between provider switches

Configure **802.1Q trunks** between SW1 – SW3 and SW2 – SW3.

![SW1 trunk](../images/qinq/sw1-trunk-config.png)

![SW2 trunk](../images/qinq/sw2-trunk-config.png)

![SW3 trunk](../images/qinq/sw3-trunk-config.png)

```
SW1(config)#int g0/1
SW1(config-if)#sw tr encap dot1q
SW1(config-if)#sw mo tr
```

## 3. Q-in-Q tunnel configuration

Now the actual "Q-in-Q" part. Everything entering the interfaces facing the customer routers gets tagged once more with **VLAN 123**.

![SW1 dot1q-tunnel](../images/qinq/sw1-dot1q-tunnel.png)

![SW2 dot1q-tunnel](../images/qinq/sw2-dot1q-tunnel.png)

```
SW1(config)#int g0/0
SW1(config-if)#switchport access vlan 123
SW1(config-if)#switchport mode dot1q-tunnel
```

| Command | Meaning |
| --- | --- |
| `switchport mode dot1q-tunnel` | Adds **one more** tag to traffic entering this port |
| `switchport access vlan 123` | Sets the outer **Q-in-Q VLAN (123)** |

VLAN 123 must exist on **SW1, SW2 and SW3**. SW1 and SW2 created it automatically when it was assigned as the access VLAN (`% Access VLAN does not exist. Creating vlan 123`), but SW3 in the middle needs it created by hand.

![SW3 vlan 123](../images/qinq/sw3-vlan-123.png)

## 4. Verification

### 4-1. Ping

![R1 ping](../images/qinq/r1-ping.png)

R1 → R2 ping succeeds (5/5).

### 4-2. `show dot1q-tunnel`

![SW1 show dot1q-tunnel](../images/qinq/sw1-show-dot1q-tunnel.png)

![SW2 show dot1q-tunnel](../images/qinq/sw2-show-dot1q-tunnel.png)

This command doesn't show much: only the **interfaces configured for dot1q tunneling**.

### 4-3. Only VLAN 123 on the trunks

The **trunks between the switches** prove that the provider switches really tunnel the customer frames.

![SW1 show interfaces trunk](../images/qinq/sw1-show-trunk.png)

![SW2 show interfaces trunk](../images/qinq/sw2-show-trunk.png)

![SW3 show interfaces trunk](../images/qinq/sw3-show-trunk.png)

Apart from VLAN 1, `Vlans allowed and active in management domain` lists only **123**. **VLAN 12 does not appear**, because the customer traffic is encapsulated inside VLAN 123.

### 4-4. No VLAN 12 in spanning-tree either

![SW1 spanning-tree vlan 12](../images/qinq/sw1-stp-vlan12.png)

![SW2 spanning-tree vlan 12](../images/qinq/sw2-stp-vlan12.png)

![SW3 spanning-tree vlan 12](../images/qinq/sw3-stp-vlan12.png)

All three switches say `Spanning tree instance(s) for vlan 12 does not exist.` The provider switches **don't care which VLAN the customer uses**; they only see VLAN 123.

## 5. Layer 2 protocol tunneling

802.1Q tunneling can also carry the customer's **Layer 2 protocols** across the provider network.

![l2protocol-tunnel options](../images/qinq/l2protocol-tunnel-options.png)

| Option | What gets tunneled |
| --- | --- |
| `cdp` | Cisco Discovery Protocol |
| `lldp` | Link Layer Discovery Protocol |
| `stp` | Spanning Tree Protocol |
| `vtp` | VLAN Trunking Protocol |
| `point-to-point` | Point-to-point protocols such as PAgP and LACP (EtherChannel) |
| `drop-threshold` / `shutdown-threshold` | Drop / shut down based on protocol packet count |

For example, tunneling CDP lets R1 and R2 see each other as CDP neighbors even with provider switches in between.

```
SW1(config-if)#l2protocol-tunnel cdp
```

---

## Key takeaways

- Q-in-Q = a **Layer 2 VPN** that adds a provider tag (**Outer**) on top of the customer tag (**Inner**).
- Customer-facing port: `switchport mode dot1q-tunnel` + `switchport access vlan <provider VLAN>`.
- The provider VLAN must exist on **every switch** along the path (create it manually on transit switches).
- Provider trunks and spanning-tree show **only the provider VLAN (123)**, never the customer VLAN (12).
- `l2protocol-tunnel` can also tunnel CDP / LLDP / STP / VTP / LACP·PAgP.
